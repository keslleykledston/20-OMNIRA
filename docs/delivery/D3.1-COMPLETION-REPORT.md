# D3.1 — Provider Model + Credential Encryption: estado real

Revisado em 2026-09-19 contra PostgreSQL real (role `omnira_app`, RLS).

## O que está em produção de código
- Domínio (`internal/channels/domain`), ports, `crypto` (AES-256-GCM, nonce fresco por Encrypt) e o adapter
  canônico `internal/channels/adapters/postgres.go` (RLS via `current_user_id()`).
  Testes de isolamento A/B, credencial e dedupe de webhook: **PASS** com Postgres real.
- `apps/api` usa `crypto` + `postgres.go`.

## Problemas encontrados
1. `migrations/000020` usa `CREATE TABLE IF NOT EXISTS channel_credentials`, mas a tabela já existia (000010):
   a coluna `nonce` **nunca foi criada**. Além disso criava policy em `current_setting('app.tenant_id')`, GUC que o
   runtime não seta → erro em toda query como `omnira_app`. Corrigido por `000022` (drop da policy).
   Aviso: `000020.down` faz `DROP TABLE channel_credentials CASCADE`, o que apagaria a tabela original de 000010.
2. `internal/channels/adapters/postgres/` (fase 3-4 do D3.1) é uma reimplementação paralela e **incompatível** com o
   schema (coluna `nonce`, `pq.Array` em `jsonb`, GUC). 11 testes falham contra Postgres real
   (só passavam/skipavam sem DB). Não é importado por nenhum código de produção.
   Recomendação: remover o pacote (o adapter canônico cobre o escopo) — decisão pendente do dono.
3. O claim anterior "phases 1-5 DONE" não tinha evidência contra Postgres real.
