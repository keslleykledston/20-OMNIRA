# ADR-0019: Visual Flow Builder, Flow Runtime e biblioteca de Templates/Packs

## Status
Proposed (2026-10-06). Implementação em fases na branch `feat/flow-builder`; **nasce desligada** (`OMNIRA_FLOWS_ENABLED=false`) e **não foi implantada**. Nenhuma tabela existente muda de semântica.

## Contexto
O OMNIRA precisa de uma camada de orquestração conversacional (chatbot de entrada, triagem, handoff) configurável pelo tenant. Já existem e **devem ser reutilizados**, não duplicados:
- `TenantContext`, RLS (`has_active_membership` + `FORCE`), `platformdb.WithTenantSession` / `WithSystemTenantSession`;
- RBAC por `permissions`/`role_permissions` (`memberships` → `role_permissions`);
- ADR-0018: `contacts.kind`, `customer_accounts`, `contact_account_links`, `user_channel_identities` (identidade interna verificada), `conversations.kind` (interna × atendimento);
- `queues`/`queue_members`/`assignment_events` e `conversations.queue_id/assigned_to_user_id` (roteamento);
- `tickets` (+ projeção externa K3G), `messages` + outbox, auditoria append-only.

## Decisão
1. **Dois planos.** *Control plane* (rascunhos, validação, publicação, versões, rollback, instalação de templates) e *Runtime* (resolver, máquina de estados, executores de node, wait/resume). O frontend nunca é o runtime; a UI só edita JSON que o backend valida e executa.
2. **Entidades separadas.** `flows` (definição lógica + rascunho editável), `flow_versions` (snapshot **imutável**, trigger no banco bloqueia UPDATE; `omnira_app` só tem SELECT/INSERT), `flow_runs`, `flow_node_executions`. `flows.active_version_id` aponta a versão para **novas** execuções; rollback = mover o ponteiro, sem tocar no histórico. Um run fica preso à versão com que começou.
3. **Templates e Packs são definições versionadas em código** (`go:embed`, JSON revisável), não linhas no banco: determinísticos, idempotentes, testáveis contra o validador/runtime reais, sem exigir escrita de sistema por `omnira_app`. O banco guarda só **instalações** (`flow_template_installations`, `flow_pack_installations`) e a proveniência no flow (`source_template_slug/version`). Instalar **clona** para um Flow `draft` do tenant (nunca publica); atualização futura do template **não** altera flows instalados. Pack = coleção versionada de templates com manifesto de dependências agregado (mapeamentos pedidos uma vez). Novos packs (MSP, Datacenter…) são só novos diretórios de definições — sem migration.
4. **Placeholders** estruturados (`{"$ref":"queue.technical"}`), nunca IDs de tenant no template. O instalador valida que cada recurso mapeado pertence ao tenant da sessão (fila, equipe, etc.) e instala em transação única (tudo ou nada).
5. **Runtime em um passo transacional por tenant.** Cada avanço roda em `WithSystemTenantSession` (tenant derivado de registro persistido, nunca de payload): trava o run (`SELECT … FOR UPDATE`), executa nodes até esperar/terminar, grava `flow_node_executions` e atualiza o run na mesma transação. **Idempotência:** `UNIQUE(tenant_id, trigger_event_id)` (id do evento/mensagem de entrada) + índice único parcial de **um run ativo por conversa**. Efeitos colaterais externos passam por outbox; efeitos locais (ticket, fila) rodam na mesma transação do passo, então reentrega não duplica.
6. **Controle da conversa.** Coluna aditiva `conversations.automation_mode` (`none` padrão = comportamento legado, `bot`, `waiting_human`, `human`), **informativa para a UI**. A autoridade de "quem fala" é derivada, sem gatilho nem mudança no claim: o runtime só age quando `automation_mode='bot'` **e** `assigned_to_user_id IS NULL`; assim que um operador assume (claim/atribuição), o bot cala sozinho. O engine só **inicia** run em conversas `conversation_kind IN ('customer_service','unclassified')` (nunca `internal`/`external_other`/spam, nem a conversa com conflito de identidade), `automation_mode='none'`, sem responsável e sem run ativo, e por padrão apenas conversas **sem run anterior** (`restart_policy=new_conversation_only`). Handoff move para `waiting_human` + `queue_id` (mesma semântica do roteamento existente: manual/round_robin). Atores `TENANT_AGENT/SYSTEM/AI_AGENT` nunca iniciam o chatbot de cliente (o ingest já separa staff via `ingestInternal`).
7. **Regras críticas determinísticas.** IA (waves posteriores, via gateway `internal/ai`/`aiusage`) só *sugere* (intent, confiança, urgência); severidade/`CRITICAL` vem de regras determinísticas. Todo node que pode falhar tem saídas `error`/`timeout`/`low_confidence` — nenhum run fica preso. Limites: `max_node_executions`, duração, profundidade de subflow, tamanho/quantidade de nodes na definição.
8. **RBAC separado:** `flow.view|create|edit|test|publish|archive`, `flow_template.view|install`, `flow_run.view`. Editar ≠ publicar.
9. **Segredos:** definições referenciam `credential_ref`; o validador rejeita campos com cara de segredo; `flow_node_executions` aplica redação antes de persistir.
10. **Feature flag:** `OMNIRA_FLOWS_ENABLED` (padrão `false`). Desligada, as rotas não são registradas e o consumidor do runtime não sobe — zero mudança para quem não ativa.
11. **Envio do bot por caminho de sistema, sem tocar no `Sender` humano.** O `messages.Sender` exige operador (`ActorID`, `conversation.claim`, conversa atribuída). O bot usa um `SystemSender` novo (arquivos novos em `internal/messages`) que reaproveita `LoadSendContext`, `SessionWindow` (janela de 24h da Meta) e o job `job.channel.send_text.v1`, com `sent_by_user_id = NULL` e idempotência própria (`UNIQUE(tenant_id, idempotency_key) WHERE sent_by_user_id IS NULL`), pois o índice existente `(tenant, sent_by_user_id, key)` não protege remetente NULL. Chave = `flow:<run_id>:<seq>`.
12. **Multi-canal.** `trigger_filter` do flow filtra por `channel_connection_id`/provider (várias linhas WhatsApp por tenant, WAHA e Meta Cloud). Capacidades do canal (botões/listas) vêm da conexão; sem suporte, `choice` degrada para menu numerado em texto. Fora da janela de 24h da Meta o bot não envia texto livre (erro `window_closed` roteável no flow).

## Consequências
- Migrations apenas **aditivas** (números após `000081`); rollback `down` testado.
- Fora de escopo agora: CRM novo, major-incident management, monitoramento vendor-specific, marketplace/import-export de flows, geração de flows por IA, upgrade assistant de templates (só metadados para o futuro).
- Pendências conhecidas e honestas ficam em `docs/flows/STATUS.md`.
